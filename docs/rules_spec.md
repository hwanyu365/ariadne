# 스펙 문서 작성 규칙 

SDD(Spec-Driven Development) 스펙 문서의 **표준 양식**과 **운영 규칙**. 모든 프로젝트/문서는 이 양식을 따라 작성하여 문서·프로젝트 간 일관성을 유지한다.

---

## 0. 문서 관리 규칙 (운영)

### 0.1 목적

스펙 문서는 **새 기능 개발 시 그 프로젝트의 요구사항·동작·제약을 파악**하기 위한 참조 문서다. 사람과 agent 가 코드를 처음부터 읽지 않고도 "무엇을 보장해야 하는가"를 알 수 있게 하는 것이 목적이며, **구현 진행 상황을 추적하는 것은 목적이 아니다**(그것은 PR·티켓이 담당한다).

### 0.2 파일

- **파일명:** 색인 `specification.md` + 기능별 `spec_{function}.md`(구성은 §0.5). 버전 번호를 붙이지 않는다 — 원본을 직접 수정하며 이력은 git 이 관리한다.
- **저장 위치:** 각 프로젝트 `CLAUDE.md` 의 `SW 스펙 문서 > 경로`를 따른다.
- **변경 방식:** 스펙이 바뀌면 **이 문서를 직접 수정**하고 PR 의 `git diff` 로 리뷰한다. **별도 diff 문서는 만들지 않는다** — 합본과 어긋날 위험만 생기고, 변경점은 `git diff` 가, 변경 이유는 커밋 메시지·PR 이 이미 담는다.
- **기준 커밋 ID:** 기능별 파일 상단(§1 문서 정보)에 스펙 정의·갱신 시점의 커밋 ID 를 표기한다.
- **변경 이력:** 기능별 파일 부록에 **티켓별 한 줄 요약**만 남긴다(색인 용도).
- **초기화:** agent 이전에 개발된 프로젝트는 스펙이 없으므로, 현재 코드/설계문서를 근거로 **as-built** 부터 정의한다.

### 0.3 무엇을 쓰고 무엇을 쓰지 않는가

문서가 방대하면 컨텍스트를 낭비하고 **낡아서 오히려 해가 된다**(agent 는 낡은 문서를 사실로 믿고 그 위에 쌓는다). 기준은 **"코드만 봐서는 알 수 없는 것"** 이다.

| 문서에 쓴다 | 코드에 두고 참조만 한다 |
| --- | --- |
| 왜 이 정책인가 (근거) | 에러 코드·상수 목록 |
| 무엇을 보장하는가 (불변조건) | 개별 메시지 문자열(i18n) |
| 어떤 제약·한계가 있는가 | 화면 전이 상세, 개별 분기 |
| 실패를 **어떻게 분류**해 다루는가 | 각 케이스의 문구 |

- **제약에는 근거(Why)를 함께 적는다.** 근거 없는 제약은 지켜지지 않는다 — 나중에 누군가 같은 시도를 반복하고, agent 는 막을 이유를 갖지 못한다.
- **기본/예외 시나리오**를 모두 명확히 기술한다.
- **연동 표기:** 다른 프로세스와 연동되는 기능은 해당 프로세스의 스펙 문서를 참조한다.
- **보안:** 평문 키·시크릿은 문서에 기재하지 않고 소스 파일 위치로만 참조한다.
- **출처 표기:** 각 항목이 `[요구사항]`(설계문서/티켓 근거)인지 `[as-built]`(현재 코드에서 확인) 인지, 확인하지 못했으면 `[확인필요]`(§2)인지 구분해 표기한다. **구현 여부는 이 태그로만 구분하며, 별도 현황표를 두지 않는다.**

### 0.4 줄바꿈 — 한 문장 한 줄

**한 문장을 한 줄로 쓴다. 문단을 폭에 맞춰 강제 개행하지 않는다.**

agent 는 어느 쪽이든 똑같이 읽는다. 이건 가독성이 아니라 **git·grep 문제**다.

- **diff.** 강제 개행된 문단은 단어 하나만 고쳐도 뒤 문장이 재배치되어 문단 전체가 변경으로 표시된다. 스펙은 원본을 직접 고치고 PR 의 `git diff` 로 리뷰하므로(§0.2), 한 단어 수정이 열두 줄 변경으로 보이면 리뷰가 성립하지 않는다.
- **grep.** 구절이 줄 경계에 걸치면 그 구절로 검색해도 나오지 않는다. 문서를 찾는 첫 수단이 grep 인데 거기서 놓친다.
- 문단 전체를 한 줄로 뭉치는 것도 답이 아니다. "이 문장만 고쳤다"가 diff 에 드러나지 않는다.
- 줄 길이는 신경 쓰지 않는다. 에디터가 soft wrap 으로 처리한다.

표·코드블록은 예외다(형식이 줄 구조를 정한다).

### 0.5 파일 구성

- **기본은 색인 + 기능별 파일.**
  - `specification.md` 는 **개요 + 색인 + 공통 제약(cross-cutting)** 만 둔다. 색인은 목차가 아니라 **작업 기준**으로 적는다(예: "유료 인증을 고친다 → spec_store.md §6").
  - 기능별 파일 `spec_{function}.md` 는 §1~§7 을 갖는 **자족 단위**다.
  - 근거: 한 기능을 고칠 때 그 파일만 읽으면 된다. 프로젝트 전체를 한 파일에 담으면 기능 수에 비례해 컨텍스트를 낭비하고, 결국 기준을 넘어 옮기는 비용이 생긴다.
- **기능 안의 요구사항·데이터·로직·테스트는 한 파일에 둔다.** 그래야 **서로 모순되는 지점을 발견**할 수 있다(예: "v1 영구 지원" NFR 과 "재서명 제거" 로직의 충돌). 기능 사이의 모순은 색인의 공통 제약에 모아 한 곳에서 본다.
- **합치고 나누는 기준은 줄 수가 아니라 결합도다.** 요구사항·TC 를 공유하는 인접 기능은 한 파일로 합친다. 한 기능 파일이 500~800줄을 넘으면 그 기능을 하위 단위로 더 나눈다.
- **분할 축은 카테고리가 아니다.** `architecture/requirements/...` 로 가르면 요구사항과 그 로직·테스트가 갈라져 추적성이 깨진다. 각 파일이 §1~§7 을 갖는 **자족 단위**로 나눈다. 프로젝트 성격에 따라 축을 고른다:

  | 프로젝트 | 분할 축 | 예 |
  | --- | --- | --- |
  | 라이브러리·서버 | **하위 시스템** | 모듈 서명 / 라이선스 코드 / 클라이언트 인증 |
  | **UI 애플리케이션** | **사용자 스토리·유스케이스(US/UC)** | 모듈 설치 / 유료 모듈 인증 / 데이터 가져오기 |

  UI 는 성공·실패·사용자 피드백이 **사용자 행위 단위**로 정의되고, 한 행위가 여러 컴포넌트를 가로지른다(예: "모듈 설치" = 화면 + DRAS + 검증 + 저장). 코드 구조로 가르면 한 시나리오가 여러 파일로 흩어져 "이 동작이 실패하면 사용자에게 무엇을 보여주는가"를 한 곳에서 볼 수 없다.
  - UC 는 **사용자가 달성하려는 목표** 단위다. "버튼 클릭"은 UC 가 아니다.
  - 각 UC 는 **독립적으로 검증 가능**해야 한다. 그 UC 하나만 구현해도 사용자에게 가치가 전달되는지 물어, 되지 않으면 잘못 자른 것이다(인접 UC 와 묶거나 경계를 다시 긋는다).
  - UC 에 **우선순위(P1/P2/P3)** 와 그 근거를 적는다. P1 은 단독으로 최소 제품이 되는 것이다. 파일 분할 순서와 작업 순서가 여기서 나온다.
  - 한 UC 가 인접 UC 와 요구사항·TC 를 대부분 공유하면 묶는다.

### 0.6 프로젝트 대원칙

기술 스택·보안 원칙·아키텍처 제약 등 **모든 작업에 적용되는 규칙**은 스펙이 아니라 프로젝트 `CLAUDE.md` 에 둔다. agent 가 항상 읽는 파일이므로 별도 문서를 만들 필요가 없다.

### 0.7 설계 내용은 스펙에 쓴다

**구조, 방안 비교, 기각한 대안, 결정 근거는 별도 설계 문서로 두지 않고 해당 기능 스펙에 쓴다.**

- 근거: 설계와 스펙을 문서로 가르면 요구사항과 그 근거 중 한쪽만 고쳐져 어긋난다. 근거가 요구사항 옆에 없으면 지켜지지 않는다(§0.3).
- 위치
  - 문제가 생기는 구조·흐름 → §1 목적
  - 선택한 방안과 기각한 대안 → §6 설계 결정
  - 여러 기능에 걸친 제약 → 색인 `specification.md` 의 공통 제약
- **쓰지 않는 것:** 사건 경위·실측 타임라인. 특정 시점에 묶인 정보라 낡는다 → 티켓·PR 에 둔다.
- 여러 프로젝트를 아우르는 제품·SW 종합 구조는 기능 스펙이 아니라 전역 종합 구조 문서가 담당한다.

## 1. 섹션 구성 규칙

표준 섹션은 아래 §1~§7. **해당 없는 섹션은 생략**한다(불필요한 자리채움 금지). 단 **섹션 번호는 표준 번호를 유지**한다 — 예: UI가 없는 라이브러리는 §5(UI/UX)를 생략하고 §6·§7 번호는 그대로 둔다.

### 1.1 인수 시나리오는 Given-When-Then 으로 쓴다

동작을 산문으로 적으면 "정상 동작해야 한다" 같은 검증 불가능한 문장이 남는다. 성공·실패·사용자 피드백을 **전제 / 행위 / 결과** 로 끊어 적으면 그대로 TC 가 된다.

```
Given  유료 모듈이 설치되어 있고 activate code 가 없다
When   사용자가 그 모듈을 실행한다
Then   실행이 차단되고, 인증이 필요하다는 안내와 인증 화면 진입 경로를 제시한다
```

- **실패 경로를 반드시 함께 적는다.** UI 스펙에서 빠지기 쉬운 쪽이 실패인데, 사용자가 실제로 막히는 지점은 거기다.
- Then 은 **관측 가능한 결과**로 적는다. "검증한다"가 아니라 "무엇이 보이는가 / 무엇이 막히는가".
- 문구 자체(i18n 메시지 원문)는 코드에 두고 문서에는 **어떤 종류의 피드백인지**만 적는다(§0.3).

## 2. 요구사항 라벨링 규칙

요구사항에는 **카테고리별 ID**를 부여한다:

| 접두      | 카테고리                       | 설명                              |
| ------- | -------------------------- | ------------------------------- |
| `US#n`  | User Story                 | "~로서 ~하기 위해 ~을 원한다" 형태의 사용자 스토리 |
| `FR#n`  | Functional Requirement     | 시스템이 수행해야 하는 구체적 동작             |
| `NFR#n` | Non-Functional Requirement | 성능·보안·호환성·확장성 등 제약 조건           |
| `BR#n`  | Business Rule (선택)         | 비즈니스 정책/규칙 (필요 시)               |
| `TC#n`  | Test Case                  | 테스트 케이스(§7). 검증 대상 요구사항 ID를 명시  |

- ID는 문서 내에서 **고유**하며, 요구사항이 바뀌어도 **ID를 유지**한다(추적성).
- §6 로직/정책·§7 테스트는 관련 요구사항 ID를 **역참조**한다(예: `[FR#1]`, `TC#3 [FR#1]`).

**출처 태그**와 별개로, **확인되지 않은 것은 반드시 표시한다.**

| 태그 | 의미 |
| --- | --- |
| `[요구사항]` | 설계문서·티켓에 근거가 있다 |
| `[as-built]` | 현재 코드에서 확인했다 |
| **`[확인필요]`** | **근거를 확인하지 못했다.** 무엇이 불확실한지와 확인 방법을 함께 적는다 |

`[확인필요]` 없이 그럴듯하게 채운 문장은 **문서에서 가장 위험한 종류**다 — 읽는 사람도 agent 도 그것을 확인된 사실로 믿고 그 위에 쌓는다. 코드에서 확인되지 않으면 추측해 적지 말고 표시한다. 스펙 리뷰는 `[확인필요]` 를 하나도 남기지 않는 것을 통과 조건으로 한다.

### 2.1 추적성 — 양방향 (필수)

역참조(TC → 요구사항)만으로는 **요구사항이 구현·검증에서 누락된 것을 잡지 못한다.** 실제로 스펙에만 존재하고 코드에는 없는 계약이 발생한 사례가 있다(SWDEV-6669: manifest 가변 필드 해시 제외). 그래서 정방향도 강제한다.

- **§3 요구사항(US/FR/NFR/BR)과 §4 데이터·API 계약의 각 항목은 대응 TC를 가져야 한다.** TC가 없는 항목은 **스펙 미완성**으로 보고, 스펙 리뷰에서 통과시키지 않는다.
- **§7 의 TC 번호는 테스트 코드에 그대로 드러나야 한다**(테스트 이름 앞에 `TC#n`). 코드에서 `TC#n` 을 grep 해 스펙과 대조할 수 있어야 하며, 대조되지 않는 TC는 미구현으로 본다.
- 구현이 소비처 저장소에 있어 이 저장소에서 검증할 수 없는 TC는 §7 표의 비고에 그 사실과 담당 저장소를 명시한다(예: `(통합 — dart-platform)`). **비워두지 않는다.**

### 2.2 완료 판정 (필수)

"테스트가 통과했다"는 완료 근거가 아니다. 그 테스트가 스펙에서 도출된 것인지 확인되지 않기 때문이다. 기능 구현을 마쳤다고 판단하기 전에 **스펙 항목 전수 대조**를 수행한다.

- §3·§4·§6 의 각 항목에 대해 `구현 위치 / 검증 TC` 를 확인한다. 하나라도 비면 미완료다.
- 대조는 **스펙 항목 단위**로 한다. 기능 덩어리(예: "v2 서명 완료")로 뭉뚱그리면 하위 계약의 누락이 가려진다. 실제로 "manifest 일부 필드를 해시에서 제외한다"는 스펙 항목이 구현되지 않은 채 남아 있었고, 덩어리 단위로 봤다면 발견되지 않았다.
- 대조 **결과는 문서에 남기지 않는다.** 진행 상황은 PR·티켓이 담당한다(§0.1). 문서에는 `[요구사항]`/`[as-built]` 태그만 남는다.
- **커밋 메시지에 스펙 문구를 그대로 옮기지 않는다.** 의도가 아니라 실제로 구현·검증된 내용만 적는다. 스펙 복붙은 미구현을 "완료"로 기록해 발견을 지연시킨다.

# 표준 문서 구조

## 1. 개요 (Overview)

- **문서 정보:** 문서명 / 작성자 / 작성일 / 최종 수정일 / 버전 / **기준 커밋 ID**
- **프로젝트·기능명:** 개발 대상 또는 기능의 명칭
- **목적 (Why):** 왜 개발하는지, 어떤 문제를 해결하는지

## 2. 목표 및 범위 (Goals & Non-Goals)

- **주요 목표 (In Scope):** 이번 스펙으로 구현할 핵심 기능·결과물
- **제외 범위 (Out of Scope):** 이번 주기에서 다루지 않는 것

## 3. 요구사항 (Requirements)  — §2 라벨링 적용

- **사용자 스토리 (US#)**
- **기능 요구사항 (FR#)**
- **비기능 요구사항 (NFR#)** — 성능/보안/호환성/확장성

## 4. 데이터 및 API 스펙 (Data & API Spec)

- **데이터 모델:** 주요 데이터 구조/스키마/타입(JSON 필드·타입 등)
- **API 명세 — 프로젝트 유형별로 표기:**
  - **REST 서비스:** Method(GET/POST/PUT/DELETE) / Endpoint / Request(파라미터·Body) / Response(성공·실패 구조)
  - **라이브러리·모듈:** 공개 클래스·함수 / 시그니처 / 반환 / 예외 계약

## 5. 화면 및 UI/UX 명세 (UI/UX Spec)

- **화면 흐름(Flow):** 기능에 따른 화면 이동 경로
- **화면 상세(Wireframe/Mockup):** 구성 요소·버튼·입력 필드
- *(UI가 없는 프로젝트는 이 섹션을 생략한다. 단 소비처 화면 흐름이 계약에 관여하면 §6에서 참조한다.)*

## 6. 동작 로직 및 정책 (Logic & Policies)

- **비즈니스 로직:** 조건 분기, 예외 처리 규칙, 계산식 — 관련 `[FR#/NFR#/BR#]` 역참조
- **상태 다이어그램:** 시스템·데이터의 상태 변화 과정
- **설계 결정:** 선택한 방안과 기각한 대안, 각각의 근거(§0.7)

## 7. 테스트 및 검증 기준 (Testing & Verification)

- **유닛 테스트 케이스 (TC#):** 시나리오 + 검증 대상 요구사항 ID (예: `TC#1 [FR#1]`)
- **통합/QA 테스트:** 기능 완료 판단을 위한 필수 검증 항목
